# SIMShift design review

## Findings

1. **HIGH — The no-Internet AWS bundle does not specify a base-model layout that the pinned Decider loader can consume offline.** **Where:** `docs/aws-deployment.md` “Offline bundle contract” and “Services”; `docs/decider-api.md` manifest example; `design.md` “AWS deployment artifacts.” The bundle places the pinned base under a logical `models/base` artifact, but the inspected Decider source at `modeling.py::StrandsDeciderModel._load_torso` calls `AutoConfig`/`AutoModel`/`AutoTokenizer.from_pretrained(config.base_model, revision=config.base_revision)` with `config.base_model == "Qwen/Qwen3.5-2B-Base"`. Nothing in the design rewrites that identifier to the local snapshot or installs the snapshot in a Hugging Face cache layout, and neither `HF_HOME` nor offline-mode environment variables are defined. On the selected private host, startup can therefore attempt Hugging Face access and fail despite the base files being present. This blocks the only designed AWS execution path. **Concrete fix:** choose and specify one tested layout. Prefer packaging the complete SHA-pinned Hub snapshot in the exact Hugging Face cache structure, setting `HF_HOME` to that promoted directory and `HF_HUB_OFFLINE=1`/`TRANSFORMERS_OFFLINE=1` in `decider.service`, and retaining the original repo ID/revision in the checkpoint. Enumerate every required tokenizer/config/weight shard, not illustrative files. Add an acceptance test that starts `strands-decider serve` with network disabled and reaches matching `/health`; fail the bundle build if any Hub request is attempted.

2. **HIGH — The private-host bootstrap has no executable stage-zero path or complete AMI prerequisite contract.** **Where:** `docs/aws-deployment.md` “Reviewable files,” “Offline bundle contract,” and “Endpoint and bootstrap preflight.” `scripts/bootstrap-host.sh` is said to download, verify, extract, and promote the archive, while the archive itself is also said to contain the bootstrap scripts. The design never states how that script reaches a fresh instance before extraction (inline UserData, pre-baked AMI, or a separately versioned object). It also does not require the selected AMI to contain the tools needed before the bundle is available—SSM agent, CA roots, SigV4-capable S3 client, SHA-256 utility, tar/zstd support, Python/runtime tooling, and, for CUDA, a compatible driver/toolkit boundary. With no NAT, implementation cannot repair a missing prerequisite. **Concrete fix:** define a minimal stage-zero bootstrap embedded verbatim in CloudFormation UserData (with a test that the embedded bytes are generated from the reviewed source) or pin a pre-baked AMI build. Add an explicit AMI contract and preflight for architecture, OS, SSM agent, download client, decompressor, disk space, Python/glibc, and GPU driver/CUDA compatibility. Stage zero must fetch the exact versioned object, verify external metadata, extract stage one, and only then run the bundled bootstrap. Add a clean-instance integration test before treating the template as deployable.

3. **MEDIUM — The mandatory on-host network checks require EC2 read APIs that the runtime role does not allow.** **Where:** `docs/aws-deployment.md` “CloudFormation contract” and “Endpoint and bootstrap preflight” steps 2, 3, and 7. Bootstrap must inspect the actual route table, exact S3 gateway endpoint ID, interface endpoint settings, and absence of exposed routes/listeners, but the listed instance-role permissions contain no `ec2:DescribeRouteTables`, `ec2:DescribeVpcEndpoints`, `ec2:DescribeSecurityGroups`, or `ec2:DescribeNetworkInterfaces`. CloudFormation-provided expected IDs do not prove actual route/endpoint state, and local routing cannot establish security-group exposure. Thus a conforming least-privilege implementation cannot perform its own fatal preconditions. **Concrete fix:** either (a) add the minimum read-only EC2 describe actions (with `Resource: "*"` where AWS does not support resource scoping), document exactly which checks use each action, and validate that no mutation action exists; or (b) move those checks to the explicitly authorized operator preflight and pass a versioned attestation into bootstrap, reducing on-host checks to connectivity and exact-object retrieval. Make one component the owner rather than requiring impossible duplicate verification.

4. **MEDIUM — A denied profile proposal has no defined terminal behavior, allowing a second profile-evaluation dispatch for which no deterministic effect exists.** **Where:** `design.md` “Bounds and orchestration” and “Concrete failure behavior”; `docs/simulation-scope.md` “Filtering and per-action behavior” and the two fixtures. `evaluate_profile_change` is removed for no target, reachability, transition limit, or in-flight state, but not after its first action occurrence. Each fixture defines only occurrence 1 for that action. The runner explicitly terminates escalation and forbids retry after profile delivery timeout/failure, but does not say whether a final gate denial terminates or returns to observation. If it loops after `--approval denied`, the unchanged target remains eligible and Decider may select profile evaluation again, yielding an undefined occurrence-2 effect and a new proposal/tool-call ID rather than duplicate suppression. **Concrete fix:** make every final gate denial terminal for this slice: emit `proposal_blocked`, then `run_escalated` with a stable `PROFILE_PROPOSAL_BLOCKED` reason, and perform no further decision. Alternatively remove profile evaluation after action count 1 and define the subsequent route, but do not leave both behaviors valid. Add a denied-Brazil production-loop test asserting one proposal, one blocked audit, zero transition records, unchanged profile, and no second Decider/tool call.

5. **MEDIUM — The real `OFFLINE` production characterization is not reproducible from the design because its exact Decider requests are unspecified.** **Where:** `docs/decider-api.md` “Exact choice request” and “Integration-test contract”; `design.md` “Test strategy and acceptance”; `docs/simulation-scope.md` OFFLINE behavior. The document gives one exact initial Brazil payload and descriptions for only four labels. `OFFLINE` initially includes `investigate_device`, `investigate_data_path`, and `escalate_or_wait`, then changes its option set and observation after each diagnostic. No canonical description is defined for `investigate_data_path` (or for all six actions in one normative registry), nor is the exact request-builder rule declared for every iteration. Prompt wording and option order can affect the required real-model path, so multiple implementations can satisfy the prose but produce different characterization results. **Concrete fix:** define a single ordered six-entry `Action -> QuestionOption(description)` registry and a deterministic projection/request-builder algorithm used on every iteration. Include golden request JSON for OFFLINE revision 0 and each reachable post-diagnostic revision, then run those exact requests against the pin and record the observed sequence. The production test should assert the bounded coordinator reaches safe escalation and no transition, while permitting only the explicitly characterized diagnostic ordering.

6. **MEDIUM — The trace contract omits the Strands tool-host model even though the design promises to label that test double independently.** **Where:** `requirements.md` FR12; `design.md` “Filtering, model/effective decisions, and direct dispatch” and “Trace design”; `docs/architecture.md` “Trace event schemas.” Local runs construct the real Strands `Agent`/tool executor with an inert `LocalTestDoubleModel`, but `run_started` requires statuses only for `decider`, `strands_dispatch`, `explainer`, `telecom_simulator`, and `aws_deployment`. The prose says the inert host model and deterministic explainer are “separately labeled,” yet there is no required field/event for the host model. A trace can therefore label Strands dispatch `REAL` without disclosing the model object backing that Agent. **Concrete fix:** add mandatory independent fields such as `strands_framework_dispatch=REAL`, `strands_tool_host_model=LOCAL_TEST_DOUBLE|REAL`, and `explainer_model=LOCAL_TEST_DOUBLE|REAL`, plus provider/model identifiers only for real models. Assert in local and AWS tests that the host-model invocation count is zero and that its status is still present; do not collapse framework execution and model provenance into one status.

7. **MEDIUM — The implementation scope still puts extensive supply-chain and private-network hardening on the critical path ahead of the requested working vertical slice.** **Where:** `requirements.md` FR15–FR16 and AC16–AC18; `design.md` “Locked stack,” “AWS deployment artifacts,” and test strategy; `docs/aws-deployment.md` throughout. The authoritative request prioritizes the first functioning, testable agent. The design makes a deterministic archive format, Merkle roots, private endpoint topology, stage scripts, custom IAM validators, CloudFormation, CPU/CUDA wheelhouses, and 18 broad acceptance checks part of the same slice as the still-unimplemented BR/OFFLINE coordinator. These are useful hardening tasks, but they substantially exceed what is needed to prove causal Decider routing and can consume the implementation window before any agent runs. Findings 1–3 also show that this extra path is not yet executable. **Concrete fix:** revise `requirements.md` and the plan into ordered gates: (A) runnable local BR/OFFLINE CLI with real Decider, direct Strands dispatch, deterministic gates/simulator, traces, and default tests; (B) one minimal, measured EC2+Bedrock deployment proving the same path; (C) offline/private-subnet bundle hardening and extended validators. Gate A must be completed and demonstrated before C starts. Keep C as required only if the entrant explicitly chooses the no-NAT topology; do not let it block the first runnable artifact.

## Verified Assumptions

- Both complete source documents, all three research/environment reports, `requirements.md`, `design.md`, and all four design-authored `docs/*.md` files were read in full.
- The rules require a working AWS agent using Decider 2B for a meaningful decision and Bedrock for generative functionality, plus the public repository/reusable pattern, article, video, license, and tags. This reviewed two-scenario CLI remains an intermediate slice rather than the complete three-scenario/UI submission described as the handoff MVP.
- The immutable Decider source, checkpoint, and base pins in the design match the validated research: source `930e6d5de16309be32579f5631a7369a3322140c`, checkpoint `216d1ccb46a9e9b036eb9187b248db98480f77d4`, and base `b1485b2fa6dfa1287294f269f5fb618e03d52d7c`.
- Direct source inspection confirms the checkpoint loader retains the remote base identifier and passes it with the pinned revision to Transformers `from_pretrained`; this verifies finding 1 rather than relying on the design’s deployment claim.
- The verified Decider contract is correctly represented: `POST /v1/systemone`, typed `choice`/`noul`/`score`, schema-level 2–255 choices, choice probabilities and derived confidence, optional HTTP `latency_ms`, and `/health`. Preserved real health reports `num_slots=24`.
- A fresh review-time invocation of the exact initial Brazil request shown in `docs/decider-api.md` against the preserved pinned real FastAPI app returned HTTP 200, `evaluate_profile_change`, probability `0.5033`, and confidence `0.3377`. On this local CPU execution it therefore clears the provisional `0.20` floor. This is one observation, not calibration or AWS/GPU proof.
- The validated Strands research supports `strands-agents==1.61.1`, `@tool` registration, exact direct calls through `agent.tool.<name>(...)` without model tool selection, and `BedrockModel(region_name=..., model_id=...)`. The causal dispatch architecture is sound if implemented as specified.
- The option prefilter, fixed dispatch allowlist, model/effective-choice split, proposal-only profile tool, proposal-bound approval, pure preview/final gates, lock/recheck, atomic reservation/consumption, non-command blocked audit, and dual registration/telemetry checks provide a deterministic safety design, subject to the denied-flow ambiguity in finding 4.
- Applying the normative deterministic calculation to Brazil seed `20261018` gives registration `3178/3200 = 0.993125` and telemetry `3156/3200 = 0.98625`, both above the `0.95` thresholds.
- The `OFFLINE` capability and reachability rules exclude direct retry, operator reselection, and profile evaluation, and the forced policy proposal is designed to deny with no command or profile mutation. Finding 5 concerns reproducible model routing, not this deterministic safety boundary.
- The observed 11.234 GiB CPU RSS exceeds AgentCore microVM’s documented 8 GiB ceiling, so rejecting that host and considering persistent EC2 is consistent with the research.

## Unverified/Wrong Assumptions

- **Wrong as currently specified:** placing a verified base snapshot at an arbitrary `models/base` path is sufficient for the upstream Decider loader to find it with no network.
- **Unverified and incomplete:** a fresh private EC2 instance can obtain and execute `bootstrap-host.sh` and already has every required stage-zero/runtime/CUDA prerequisite.
- **Wrong as a permissions contract:** the listed runtime role can perform all mandatory route, endpoint, interface, and exposure inspections without EC2 describe permissions.
- **Unspecified:** a profile gate denial terminates the run; without this rule, a valid second profile-evaluation attempt has no fixture effect.
- **Unverified:** the exact iterative OFFLINE prompt/option sequence produces the required real-model characterization; no complete normative request sequence is present.
- **Incomplete:** the runtime trace independently discloses the inert Strands host model; the required status schema currently omits it.
- **Unverified but correctly labeled elsewhere:** Bedrock model/profile authorization, AWS credentials, VPC/endpoints, EC2 quota/capacity, CUDA compatibility, GPU behavior, AWS latency/cost, and a real AWS-hosted run. The environment report confirms none was tested.
- **Unverified:** the provisional confidence floor `0.20` is calibrated for SIMShift. The observed initial Brazil result exceeds it, but one fixture/result does not establish reliability.
